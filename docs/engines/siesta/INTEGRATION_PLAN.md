## GEN Steps Mapping

All needed GEN steps already exist in `GenStepRegistry`. **No changes to gen_steps.py needed.**

| GEN Step | SPEC Step | Siesta Capability | Notes |
|----------|-----------|-------------------|-------|
| `scf` | `siesta_scf` | SCF energy calculation | Core. Includes optional bands/PDOS in same run |
| `relax` | `siesta_relax` | Geometry optimization | CG/Broyden/FIRE. VC is a parameter |
| `md` | `siesta_md` | Molecular dynamics | Verlet/Nose/NPR/Anneal ensembles |
| `bands` | `siesta_bands` | Band structure | Computed in SCF run via BandLines block |
| `dos` | `siesta_dos` | Density of states | Computed from eigenvalues |

### Siesta-Specific Workflow Considerations

**Critical**: Unlike QE, Siesta computes bands and PDOS **within the same run** as SCF. There is no separate post-processing executable. This means:

1. `siesta_scf` can be configured to also produce bands/PDOS output (via FDF parameters)
2. `siesta_bands` and `siesta_dos` would be separate SPEC steps if the user wants to do a standalone bands/DOS calculation, but typically they are parameters within `siesta_scf`
3. For the initial integration, we recommend supporting `scf`, `relax`, and `md` as the primary step types, with bands/DOS as FDF parameters within SCF

**Decision**: Register `siesta_bands` and `siesta_dos` as valid step types for completeness and compatibility with the GEN step system, but in practice they will be thin wrappers that configure the FDF appropriately and run the same `siesta` binary. The handler can detect these and add appropriate FDF blocks.

## Driver Implementation Details

### `driver.py` — SiestaDriver

```python
class SiestaDriver(BaseEngineDriver):
    PREFIX = "siesta"
    SUPPORTED_GEN_STEPS = frozenset({"scf", "relax", "md", "bands", "dos"})

    # Properties
    engine_family → "siesta"
    display_name → "Siesta"
    driver_api_version → "1.0.0"

    # Methods
    get_step_type_specs() → [
        StepTypeSpec("siesta_scf", engine="siesta", executable="siesta", ...),
        StepTypeSpec("siesta_relax", engine="siesta", executable="siesta", ...),
        StepTypeSpec("siesta_md", engine="siesta", executable="siesta", supports_restart=True, ...),
        StepTypeSpec("siesta_bands", engine="siesta", executable="siesta", ...),
        StepTypeSpec("siesta_dos", engine="siesta", executable="siesta", ...),
    ]
    get_handler() → siesta_step_handler
    get_recipe_class() → SiestaRecipe
    get_workdir_policy() → WorkdirPolicy.ISOLATED
    get_capabilities() → {"scf", "relax", "md", "bands", "dos", "periodic", "molecular", "mpi"}
```

### `recipe.py` — SiestaRecipe (Directory-state)

**Archetype choice rationale**: Siesta is closest to the Directory-state archetype because:
- It accumulates files in the working directory (`.DM` for restart)
- Unlike QE, it doesn't use a shared `outdir/` — each step's files are named by `SystemLabel`
- But it does use file-based restart (`.DM` file), similar to QE's charge density
- ISOLATED workdir policy (each step gets its own directory) with explicit DM staging for restart

**Key behaviors**:
1. One job per step
2. Working dir: `calc/raw/{step_ulid}/`
3. Pseudopotential files staged into working dir (`.psml` or `.psf`)
4. For restart steps: copy `.DM` from reference SCF step
5. FDF file generated by writer, placed in working dir
6. Command: `siesta < {label}.fdf > {label}.out 2>&1`

### `handler.py` — siesta_step_handler

**Execution flow**:
1. Receive `Job` with step data
2. Create working directory
3. Stage pseudopotential files (from project/system pseudopotential mapping)
4. Generate FDF input file (via writer)
5. Optionally stage `.DM` restart file from prior step
6. Execute `siesta < input.fdf > output.out`
7. Check `0_NORMAL_EXIT` marker
8. Parse output files (via parser)
9. Return `JobResult` with parsed data

### `writer.py` — FDF Writer

Adapted from `docs/engines/siesta/scripts/siesta_input_writer.py`:
- Converts QMatSuite step parameters to FDF format
- Handles species/pseudopotential mapping
- Generates k-point grid
- Configures SCF, relaxation, MD parameters
- Adds bands/PDOS blocks as needed

### `parser.py` — Output Parser

Adapted from `docs/engines/siesta/scripts/siesta_parser.py`:
- Parses `.out`, `.EIG`, `.FA`, `.STRUCT_OUT`, `.XV`, `FORCE_STRESS`, `OUTVARS.yml`, `.MDE`, `.DOS`, `.PDOS.xml`
- Returns structured data for `JobResult`
- Checks convergence and normal exit

## Pseudopotential Handling

Siesta requires pseudopotential files (`{SpeciesLabel}.psml` or `{SpeciesLabel}.psf`) in the working directory. These need to be:

1. Mapped in `calculation.yaml` species/pseudopotential configuration
2. Staged into each step's working directory by the recipe/handler
3. Named to match the species label in the FDF `ChemicalSpeciesLabel` block

This is analogous to how QE handles UPF files and VASP handles POTCAR. The handler should resolve pseudopotential paths from the calculation configuration and copy/symlink them into the working directory.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Bands/PDOS not separate steps in Siesta | Handle as FDF parameters within SCF step; register spec types for compatibility |
| Pseudopotential staging | Follow existing pattern (QE UPF staging) |
| SystemLabel conflicts in shared dir | Each step gets isolated workdir with unique SystemLabel |
| DM restart binary format | Simply copy the `.DM` file (no parsing needed) |
| No changes needed in kernel | Verified: all needed GEN steps exist, driver plugin model works |
