# ORCA Integration Exploration and Design Plan

**Date**: 2025-01-XX  
**Status**: Exploration Phase (No Implementation)  
**Goal**: Design ORCA integration into QMatSuite's engine/step/chain/artifact architecture, consistent with QE (executable) and PySCF (Python/in-proc) patterns

---

## 1. ORCA Workflow + File Model

### 1.1 Execution Model

**A) CLI Invocation Patterns**

ORCA is executed as a command-line executable:
```bash
orca input.inp > output.out 2>&1
```

- **Input file**: `.inp` format (text file with ORCA input syntax)
- **Output redirection**: Standard output and error are redirected to `.out` file
- **Working directory**: ORCA reads from and writes to the current working directory
- **No command-line flags**: ORCA does not accept calculation parameters via command-line; all parameters are in the input file

**B) Parallelism Model**

ORCA handles parallelism internally via the `%pal` (Parallelization) block:
```plaintext
%pal
nprocs 4
end
```

**Key Rules**:
- ORCA manages MPI internally; **DO NOT** wrap ORCA execution with `mpirun`/`mpiexec`
- The `nprocs` setting in `%pal` controls the number of processes
- ORCA can also use OpenMP for threaded parallelism (via `%maxcore` or environment variables)
- Hybrid MPI+OpenMP is supported but complex; typical usage is MPI-only or OpenMP-only

**QMatSuite Mapping**:
- `EngineConfig.mpi_cores` → `%pal nprocs` in input file
- `EngineConfig.omp_threads` → OpenMP threads (via environment or `%maxcore`)
- **Critical**: Never use `mpi_command` wrapper; ORCA must be launched directly

**C) Output Artifacts**

**Restartable/Seed Artifacts**:
- **`.gbw` files**: Binary wavefunction files containing orbitals, density, and other SCF data
  - Generated by DFT/HF calculations
  - Can be used as initial guess for subsequent calculations via `! MORead` or `%moinp`
  - **This is the primary "seed artifact" for ORCA** (analogous to QE's `data-file-schema.xml` outdir)

**Stable for Analysis**:
- **`.out` file**: Main output file with detailed calculation logs and results
  - Contains energy, convergence information, property tables, etc.
  - Parsable but verbose; preferred to use property files when available
- **`.prop` files**: Structured property files (ORCA 5.0+)
  - Contains calculated properties in machine-readable format
  - Can be converted to JSON using ORCA's `orca_2mkl` utility or parsing tools
  - **Preferred for analysis** (analogous to QE's parsed JSON artifacts)
- **`.molden` files**: Molecular orbital information for visualization
  - Generated via `%output Print[P_Molden] "file.molden" end` block
  - Compatible with visualization tools (VMD, Molden, etc.)

**Scratch Files (Can Be Deleted)**:
- **`.tmp` directory**: Temporary files created during execution
- **`.hess` files**: Hessian matrices (can be regenerated)
- Various temporary binary files (`.pre`, `.ras`, etc.)
- Users can specify scratch directory via `%tmpdir` block

**D) Multi-Step Workflows**

**`$new_job` Mechanism** (Legacy, ORCA 4.x/5.x):
```plaintext
! DFT B3LYP def2-SVP
%pal nprocs 4 end
* xyzfile 0 1 structure.xyz

$new_job
! TDDFT
%moinp "jobname.gbw"
* xyzfile 0 1 structure.xyz
$end
```

- Multiple calculations in a single input file
- Each `$new_job` section starts a new calculation
- Can reuse GBW files via `%moinp`
- **Note**: QMatSuite's "one step = one run" model maps better to separate input files

**Compound Workflows** (ORCA 6.0+):
- ORCA 6.0 introduces `Compound` keyword for more structured multi-step workflows
- Still under development; documentation incomplete
- **Recommendation**: For MVP, use separate steps with GBW reuse (aligns with QMatSuite model)

**Typical Chaining Patterns**:
1. **DFT → TDDFT**: 
   - Step 1: DFT SCF calculation → generates `*.gbw`
   - Step 2: TDDFT calculation with `%moinp "step1.gbw"` → reads orbitals from step 1
2. **DFT → Frequency**:
   - Step 1: DFT geometry optimization → generates `*.gbw` and optimized geometry
   - Step 2: Frequency calculation with `! Freq` and `%moinp "step1.gbw"`
3. **DFT → NMR**:
   - Step 1: DFT SCF → generates `*.gbw`
   - Step 2: NMR property calculation with `%moinp "step1.gbw"`
4. **CCSD → EOM-CCSD**:
   - Step 1: CCSD calculation → generates `*.gbw` (with correlated orbitals)
   - Step 2: EOM-CCSD calculation with `%moinp "step1.gbw"`

**E) Capability Overview**

**Method Families**:
- **Hartree-Fock (HF)**: RHF, UHF, ROHF
- **Density Functional Theory (DFT)**: Many functionals (B3LYP, PBE, PBE0, etc.)
- **Møller-Plesset Perturbation Theory**: MP2, MP3, MP4
- **Coupled Cluster**: CCSD, CCSD(T), CCSDT, etc.
- **Multireference Methods**: CASSCF, NEVPT2
- **Excited States**: TDDFT, TDA, EOM-CCSD, STEOM-CCSD

**Property Families**:
- **Geometry Optimization**: `! Opt` (gradient-based optimization)
- **Vibrational Frequencies**: `! Freq` (harmonic frequencies, IR/Raman intensities)
- **Excited States**: `! TDDFT`, `! TDA`, `! EOM-CCSD`
- **NMR Properties**: `! NMR` (chemical shifts, spin-spin couplings)
- **Other Properties**: Polarizabilities, hyperpolarizabilities, EPR, etc.

**Common Combinations**:
- DFT single-point energy
- DFT geometry optimization
- DFT optimization + frequency
- DFT optimization + frequency + NMR
- DFT → TDDFT (excited states)
- HF → MP2 (correlation energy)
- CCSD → EOM-CCSD (excited states from correlated wavefunction)

### 1.2 Reusable vs One-Shot Components

**Reusable**:
- **GBW files**: Can be reused as initial guess for subsequent SCF/DFT calculations
  - Most common reuse pattern: DFT SCF → property calculation (TDDFT, NMR, Freq)
  - Also used: SCF → post-HF (MP2, CCSD) if using frozen-core orbitals
- **`.molden` files**: Reusable for visualization (but typically regenerated per calculation)

**One-Shot** (Not Reusable):
- **Output files (`.out`)**: Calculation-specific logs; not reused
- **Property files (`.prop`)**: Analysis artifacts; generated per calculation
- **Most post-HF steps**: CCSD(T), EOM-CCSD typically need fresh GBW (though can seed from SCF)
- **Frequency calculations**: Require optimized geometry; not typically restarted
- **Scratch files**: Temporary; can be deleted

**Reuse Semantics Summary**:
- **Primary reuse**: GBW files from SCF/DFT calculations
- **Typical pattern**: One SCF/DFT calculation generates GBW, multiple property calculations read it
- **Not reused**: Property outputs, frequency outputs (unless same geometry), most post-HF outputs

## 2. Repository Code Review: QE and PySCF Integration Patterns

### 2.1 QE Adapter Pattern (Executable Engine)

**Architecture Summary**:

```
┌─────────────────────────────────────────────────────────────┐
│ CalculationRunner                                           │
│  └─> EngineRegistry.get("qe")                              │
│      └─> QeEngine (src/quantumvitas/engine/qe_engine.py)  │
│          └─> QuantumEspressoEngine (legacy)                │
│              └─> QECalculationRunner                       │
└─────────────────────────────────────────────────────────────┘
```

**Key Files**:
- **Engine Interface**: `src/quantumvitas/engine/base.py` (`Engine`, `EngineConfig`, `StepResult`)
- **QE Engine Adapter**: `src/quantumvitas/engine/qe_engine.py` (wraps legacy engine)
- **Legacy QE Engine**: `src/quantumvitas/core/engines/qe.py` (`QuantumEspressoEngine`)
- **QE Calculation Runner**: `src/quantumvitas/core/engines/qe_calculation.py` (`QECalculationRunner`, `StepResult`)
- **Engine Registry**: `src/quantumvitas/engine/registry.py` (`EngineRegistry`, `create_default_registry()`)

**Execution Flow**:

1. **Command Building** (`QuantumEspressoEngine.build_command()`):
   - Maps step type → executable (e.g., `"scf"` → `"pw.x"`)
   - Resolves executable path via `get_executable_path()` (handles platform-specific names)
   - Adds MPI wrapper if `config.mpi_command` and `config.mpi_cores > 1`: `[mpirun, -np, N, exe_path]`
   - Most QE steps use stdin redirection: `pw.x < input.in`
   - Wannier90 steps use command-line args: `wannier90.x seedname`

2. **Working Directory**:
   - Each calculation has `raw/` directory
   - Each step runs in `raw/` (shared directory)
   - Input files: `{step_type}.in` (e.g., `scf.in`, `nscf.in`)
   - Output files: `{step_type}.out` (stdout capture), `{step_type}.err` (stderr capture)
   - QE-specific artifacts: `data-file-schema.xml`, `*.wfc*`, etc. (in `outdir/` subdirectory if specified)

3. **Artifact Collection**:
   - Primary output: stdout capture file (`{step_type}.out`)
   - Stderr capture: `{step_type}.err`
   - QE-specific artifacts detected by presence (e.g., `data-file-schema.xml` for restart)
   - Artifacts registered in manifest via `CalculationRunner` (not in engine layer)

4. **Failure Detection**:
   - Return code check: `process.returncode == 0`
   - Sentinel file checks: e.g., `w90_preproc` requires `*.nnkp` file
   - Output parsing: Not done in engine layer (deferred to analysis layer)

5. **Parallelism**:
   - `EngineConfig.mpi_command`: e.g., `"mpirun"`, `"mpiexec"`
   - `EngineConfig.mpi_cores`: Number of MPI processes
   - `EngineConfig.omp_threads`: OpenMP threads (via `OMP_NUM_THREADS` env var)
   - MPI wrapper prepended to command: `[mpirun, -np, 4, pw.x]`
   - QE input file does NOT contain `nproc`; parallelism is external

**QE Adapter Pattern Diagram**:

```
┌─────────────────────────────────────────────────────────────┐
│ QE Engine Integration                                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Engine Interface:                                          │
│    Engine.run_step(step, working_dir) -> StepResult        │
│                                                             │
│  QE Implementation:                                         │
│    1. Generate input file: QEInputGenerator.write_file()   │
│       → {step_type}.in in working_dir                      │
│                                                             │
│    2. Build command: build_command(step_type, input, dir)  │
│       → [mpirun?, -np?, N?, pw.x]                          │
│                                                             │
│    3. Execute: subprocess.Popen(command, stdin=input.in,   │
│                  stdout={step_type}.out, stderr={step}.err)│
│                                                             │
│    4. Return StepResult:                                    │
│       - step_type, input_file, output_file,                │
│       - success (return_code==0), return_code,             │
│       - stdout/stderr (file paths), execution_time         │
│                                                             │
│  Artifacts:                                                 │
│    - Input: {step_type}.in                                 │
│    - Output: {step_type}.out (stdout)                      │
│    - QE-specific: data-file-schema.xml, *.wfc*, etc.       │
│      (in outdir/ if specified, or working_dir/)            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 PySCF Adapter Pattern (Python In-Proc Engine)

**Architecture Summary**:

```
┌─────────────────────────────────────────────────────────────┐
│ CalculationRunner                                           │
│  └─> EngineRegistry.get("pyscf")                           │
│      └─> PySCFEngine (src/quantumvitas/engine/pyscf_engine.py)
│          └─> subprocess: python -m quantumvitas.engines.pyscf
│              └─> Runner (src/quantumvitas/engines/pyscf/runner.py)
│                  └─> Direct PySCF API calls                │
└─────────────────────────────────────────────────────────────┘
```

**Key Files**:
- **PySCF Engine**: `src/quantumvitas/engine/pyscf_engine.py` (`PySCFEngine`)
- **PySCF Runner**: `src/quantumvitas/engines/pyscf/runner.py` (subprocess entry point)
- **Step Registry**: `src/quantumvitas/workflow/registry.py` (step type definitions)

**Execution Flow**:

1. **No Input Files**:
   - PySCF steps do NOT generate `.in` files
   - Parameters come from `step.yaml` → `parameters` dict
   - Runner receives `job.json` with parameters

2. **Subprocess Execution**:
   - PySCF engine never imports PySCF directly (daemon isolation)
   - Creates `job.json` file with step parameters
   - Launches subprocess: `[python, -m, quantumvitas.engines.pyscf, job.json]`
   - Subprocess imports PySCF and executes calculation

3. **Working Directory**:
   - Each step has `step_artifacts/{step_slug}/` directory
   - Artifacts: `checkpoint.chk` (PySCF checkpoint), `results.json` (structured results), `stdout.txt`
   - No input files written

4. **Artifact Collection**:
   - Primary artifact: `results.json` (structured results: energy, converged, etc.)
   - Checkpoint: `checkpoint.chk` (HDF5 format, for SCF restart)
   - Stdout: `stdout.txt` (PySCF log)
   - No `.in` files

5. **State Persistence**:
   - SCF steps: `checkpoint.chk` can be reused via `init_guess="chkfile:path/to/checkpoint.chk"`
   - Other steps: No restart artifacts (always rerun in v0)
   - State inferred from upstream steps: SCF metadata (method, xc) read from upstream `results.json`

6. **Parallelism**:
   - PySCF parallelism is handled internally (threading, BLAS, etc.)
   - `EngineConfig.omp_threads` → `OMP_NUM_THREADS` environment variable
   - No MPI wrapper (PySCF is Python-native, no MPI in standard installation)

**PySCF Adapter Pattern Diagram**:

```
┌─────────────────────────────────────────────────────────────┐
│ PySCF Engine Integration                                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Engine Interface:                                          │
│    Engine.run_step(step, working_dir) -> StepResult        │
│                                                             │
│  PySCF Implementation:                                      │
│    1. Build job.json: {step_type, parameters, working_dir} │
│       → job.json in working_dir                            │
│                                                             │
│    2. Build command: [python, -m, quantumvitas.engines.pyscf, job.json]
│                                                             │
│    3. Execute: subprocess.Popen(command, cwd=working_dir)  │
│       → Runner subprocess imports PySCF, runs calculation  │
│                                                             │
│    4. Runner writes:                                        │
│       - results.json (structured results)                  │
│       - checkpoint.chk (if SCF step)                       │
│       - stdout.txt (PySCF log)                             │
│                                                             │
│    5. Return StepResult:                                    │
│       - step_type, input_file=job.json,                    │
│       - output_file=results.json,                          │
│       - success (return_code==0), stdout/stderr            │
│                                                             │
│  Artifacts:                                                 │
│    - Job spec: job.json (transient, not versioned)         │
│    - Results: results.json (structured)                    │
│    - Checkpoint: checkpoint.chk (SCF steps only)           │
│    - Log: stdout.txt                                        │

```

### 2.3 Cross-Cutting Infrastructure

**A) Step/Calc/Project Resource Model**:

- **ULID Usage**: All resources (calculations, steps, structures) use ULIDs for unique identification
  - Location: `src/quantumvitas/core/resources.py` (`generate_resource_id()`)
  - Steps have `meta.id` (ULID) and `meta.slug` (human-readable)
  - Registry uses ULIDs for resolution: `require_step(project_root, calculation_id, step_id)`

- **Manifest System**: Tracks step execution state for incremental runs
  - Location: `src/quantumvitas/calculation/manifest.py`, `manifest_reconcile.py`
  - Manifest entries: `{kind, step_ulid, pseudo_set_sha, structure_sha, step_sha, done, run_id, timestamps}`
  - Reconciliation: Compares old manifest with current topology, determines which steps to rerun

- **Step Registry**: Centralized step type definitions
  - Location: `src/quantumvitas/workflow/registry.py`
  - Maps step types to engine families, machine types, public types
  - Defines step capabilities: `supports_incremental_skip`, `requires_upstream_step`, etc.

**B) Artifact Registry Conventions**:

- **Working Directory Layout**:
  - QE: `raw/{step_type}.in`, `raw/{step_type}.out`, `raw/outdir/` (if specified)
  - PySCF: `raw/step_artifacts/{step_slug}/results.json`, `raw/step_artifacts/{step_slug}/checkpoint.chk`
  - Analysis artifacts: `analysis/{type}.json` (separate from raw outputs)

- **Artifact Collection**: Not done in engine layer; handled by `CalculationRunner` after step execution
  - StepResult contains file paths; runner determines which files to track

**C) Job Manager / History Pipeline**:

- **Job Manager**: `src/quantumvitas/daemon/jobs.py` (`JobManager`)
  - Manages background job execution (sequential, max_workers=1)
  - Tracks job status, step progress
  - History: Job results stored in-memory (not persisted to disk)

**D) Presets / Step Templates**:

- **Workflow Templates**: `src/quantumvitas/workflow/templates.py`
  - Defines workflow families: `scf_dos`, `scf_bands`, `scf_td`, etc.
  - Templates specify step sequences and dependencies
  - Materialization: Maps generalized steps to engine-specific steps based on `engine_family`

- **Step Factory**: `src/quantumvitas/workflow/step_factory.py`
  - Centralized step creation: `create_step_doc()`, `save_step_doc()`
  - Handles ULID generation, slug rules, defaults

**E) Testing Structure**:

- **Unit Tests**: `tests/unit/` (engine-specific logic, input generation, parsing)
- **Integration Tests**: `tests/integration/` (full execution workflows, engine registry)
- **Fixtures**: `tests/conftest.py` (common test fixtures, mock engines)
- **Extended Tests**: `extended-tests/` (real QE execution, tutorial examples)

**Key Infra Components ORCA Should Reuse**:

1. **Engine Interface**: `Engine.run_step(step, working_dir) -> StepResult`
2. **Engine Registry**: Register ORCA engine in `create_default_registry()`
3. **Step Registry**: Define ORCA step types in workflow registry
4. **Manifest System**: Track ORCA step execution state (if supports incremental skip)
5. **CalculationRunner**: Execute ORCA steps via engine registry
6. **Artifact System**: Collect ORCA artifacts (GBW, out, prop files) into manifest
7. **Workflow Templates**: Define ORCA workflow families (DFT→TDDFT, etc.)

## 3. Mapping ORCA into QMatSuite: Proposed Integration Design

### 3.1 ORCA as an Executable Engine (QE-like)

**Canonical Model: One Step = One ORCA Run**

- Each QMatSuite step corresponds to a single ORCA execution
- Each step has its own input file: `{step_slug}.inp` (or `{step_type}.inp` if no slug)
- Each step runs in the calculation's `raw/` directory
- Output files: `{step_slug}.out` (or `{step_type}.out`)

**Naming and Directory Management**:

- **Input files**: `{step_slug}.inp` (preferred) or `{step_type}.inp` (fallback)
  - Examples: `dft_scf.inp`, `tddft.inp`
- **Output files**: `{step_slug}.out` (stdout capture)
- **GBW files**: `{step_slug}.gbw` (wavefunction file)
- **Property files**: `{step_slug}.prop` (if generated)
- **Working directory**: Shared `raw/` directory for all steps in calculation

**Parallelism Settings**:

- **MPI**: `EngineConfig.mpi_cores` → `%pal nprocs N` in input file
  - **Critical**: Do NOT use `config.mpi_command` wrapper; ORCA must be launched directly
  - Implementation: In `build_command()`, return `[orca_exe_path]` (no MPI wrapper)
  - Input generation: Inject `%pal nprocs {config.mpi_cores} end` block
- **OpenMP**: `EngineConfig.omp_threads` → `OMP_NUM_THREADS` environment variable
  - Optional: Also set `%maxcore` in input file (if supported)

**Command Building**:

```python
def build_command(step_type: str, input_file: Path, working_dir: Path) -> List[str]:
    # Get ORCA executable path
    exe_path = self.get_executable_path("orca")
    
    # ORCA does NOT use stdin redirection; input file is positional argument
    # Command: orca input.inp > output.out
    # But we redirect stdout ourselves, so: orca input.inp
    command = [str(exe_path), str(input_file.name)]  # Use relative path (cwd=working_dir)
    
    # NO MPI wrapper (ORCA handles MPI internally)
    # NO stdin redirection (ORCA uses positional input file argument)
    
    return command
```

**Execution**:

- Run in `working_dir` (calculation's `raw/` directory)
- Redirect stdout to `{step_slug}.out`
- Redirect stderr to `{step_slug}.err`
- Input file: `{step_slug}.inp` (already in working_dir)
- ORCA will generate: `{step_slug}.gbw`, `{step_slug}.prop` (if requested), etc.

### 3.2 Artifacts Contract (Per Step Type)

**Minimal Required Artifacts**:

- **Input file**: `{step_slug}.inp` (required for execution)
- **Output file**: `{step_slug}.out` (required; stdout capture)

**Optional/Recommended Artifacts**:

- **GBW file**: `{step_slug}.gbw` (generated by SCF/DFT steps)
  - Used as seed artifact for downstream steps
- **Property file**: `{step_slug}.prop` (if `%output` block requests it)
  - Machine-readable properties; preferred for analysis
- **Molden file**: `{step_slug}.molden` (if requested)
  - Visualization artifact

**Seed Artifacts for Downstream Steps**:

- **GBW files**: Primary seed artifact for ORCA
  - SCF/DFT steps generate GBW files
  - Downstream steps (TDDFT, NMR, Freq, post-HF) can read GBW via `%moinp "{upstream_step_slug}.gbw"`
  - **Naming constraint**: GBW filename must match input file basename (ORCA convention)
  - **Reuse strategy**: Copy or symlink upstream GBW to current step's working directory with matching name

**Analysis-First Artifacts**:

- **Property files (`.prop`)**: Structured format, preferred over parsing `.out`
  - If available, use `.prop` for analysis
  - Fallback to parsing `.out` if `.prop` not available
- **Output files (`.out`)**: Fallback for analysis (verbose, but contains all information)

**Artifact Collection Rules**:

1. **Always collect**: `.inp`, `.out`, `.err` (input and output captures)
2. **Collect if present**: `.gbw` (SCF/DFT steps), `.prop` (if requested), `.molden` (if requested)
3. **Ignore**: `.tmp/` directory, scratch files (`.pre`, `.ras`, etc.)
4. **GBW reuse**: If step has upstream dependency, ensure upstream GBW is copied/linked to current step's directory with correct name

### 3.3 Restart / Reuse Semantics

**What "Reuse" Means in ORCA**:

- **GBW file reuse**: Primary reuse mechanism
  - Upstream SCF/DFT step generates `{upstream}.gbw`
  - Downstream step uses `%moinp "{upstream}.gbw"` in input file
  - ORCA reads orbitals from GBW file as initial guess
  - **This is the standard pattern**: One SCF/DFT → multiple property calculations

**What is NOT Reusable**:

- **Most post-HF steps**: CCSD(T), EOM-CCSD typically need fresh GBW (can seed from SCF, but not from previous post-HF)
- **Frequency calculations**: Require optimized geometry; not typically restarted (always rerun)
- **Property outputs**: `.prop`, `.out` files are analysis artifacts; not reused for restart

**Robust Reuse Rules**:

1. **SCF/DFT steps**: Generate GBW files (seed artifacts)
2. **Property steps** (TDDFT, NMR, Freq): Can reuse upstream GBW via `%moinp`
3. **Post-HF steps** (MP2, CCSD): Can reuse SCF GBW (frozen-core orbitals)
4. **EOM-CCSD steps**: Can reuse CCSD GBW (correlated orbitals)

**Downstream Step GBW Handling**:

- **Naming constraint**: GBW filename must match input file basename
  - If step input is `tddft.inp`, GBW must be named `tddft.gbw` (ORCA convention)
  - But upstream GBW is `dft_scf.gbw`
  - **Solution**: Copy/link upstream GBW to current step's directory and rename to match input basename
  - Alternative: Use ORCA's `%moinp` with full path (if ORCA supports it)

- **Implementation strategy**:
  - Before step execution, check if step has upstream dependency
  - If yes, locate upstream GBW file
  - Copy (or symlink) upstream GBW to current step's directory with name matching input basename
  - Inject `%moinp "{local_gbw_name}.gbw"` into input file

**Restart Policy** (Conservative, like PySCF):

- **SCF/DFT steps**: Can be skipped if:
  - SHA hash matches (inputs unchanged)
  - GBW file exists and is readable
  - `supports_incremental_skip=True` (default for SCF/DFT)
- **Property steps**: **Always rerun** in MVP (even if SHA matches)
  - `supports_incremental_skip=False`
  - Rationale: Property calculations are fast; rerunning ensures consistency

### 3.4 Workflow Families

Define a small set of workflow families for ORCA (for future presets):

**1. DFT Single-Point**:
- **Steps**: `orca_dft_scf`
- **Inputs**: Structure, basis set, functional, charge, spin
- **Outputs**: Energy, GBW file, property file (optional)
- **User Knobs**: Functional (B3LYP, PBE, etc.), basis set (def2-SVP, def2-TZVP, etc.), convergence thresholds

**2. DFT + Frequency**:
- **Steps**: `orca_dft_scf`, `orca_freq`
- **Inputs**: Structure, basis set, functional, charge, spin
- **Dependencies**: `orca_freq` reads GBW from `orca_dft_scf`
- **Outputs**: Energy, frequencies, IR/Raman intensities, GBW, property file
- **User Knobs**: Functional, basis set, frequency calculation settings

**3. DFT + TDDFT**:
- **Steps**: `orca_dft_scf`, `orca_tddft`
- **Inputs**: Structure, basis set, functional, charge, spin, number of excited states
- **Dependencies**: `orca_tddft` reads GBW from `orca_dft_scf`
- **Outputs**: Ground-state energy, excited-state energies/oscillator strengths, GBW
- **User Knobs**: Functional, basis set, number of states, TDDFT method (TDA vs full TDDFT)

**4. DFT + NMR**:
- **Steps**: `orca_dft_scf`, `orca_nmr`
- **Inputs**: Structure, basis set, functional, charge, spin
- **Dependencies**: `orca_nmr` reads GBW from `orca_dft_scf`
- **Outputs**: Ground-state energy, NMR chemical shifts, spin-spin couplings, GBW
- **User Knobs**: Functional, basis set, NMR method (GIAO, etc.)

**5. CCSD(T) Energy (One-Shot)**:
- **Steps**: `orca_ccsd_t`
- **Inputs**: Structure, basis set, charge, spin, reference (RHF/UHF)
- **Outputs**: CCSD(T) energy, GBW (if requested)
- **User Knobs**: Basis set, frozen core options, convergence thresholds
- **Note**: Can seed from SCF GBW, but CCSD(T) is typically standalone

**6. CCSD → EOM-CCSD**:
- **Steps**: `orca_ccsd`, `orca_eom_ccsd`
- **Inputs**: Structure, basis set, charge, spin, number of excited states
- **Dependencies**: `orca_eom_ccsd` reads GBW from `orca_ccsd`
- **Outputs**: CCSD energy, EOM-CCSD excited-state energies/oscillator strengths, GBW
- **User Knobs**: Basis set, number of states, EOM-CCSD settings
- **Special**: EOM-CCSD requires correlated wavefunction (CCSD GBW), not SCF GBW

### 3.5 Analysis Strategy

**Prefer Stable Machine-Readable Outputs**:

- **Property files (`.prop`)**: Preferred if available (ORCA 5.0+)
  - Structured format, easier to parse
  - Can be converted to JSON using ORCA utilities or custom parsers
- **Output files (`.out`)**: Fallback if `.prop` not available
  - Verbose but contains all information
  - Parse energy, convergence, property tables from text

**Minimal Results for MVP**:

- **SCF/DFT steps**: Energy, convergence status, method, functional, basis set
- **TDDFT steps**: Ground-state energy, excited-state energies, oscillator strengths
- **Frequency steps**: Frequencies, IR intensities, zero-point energy, thermochemistry
- **NMR steps**: Chemical shifts, spin-spin couplings
- **Post-HF steps**: Correlation energy, total energy

**Future Expansions**:

- Full property file parsing (all properties in `.prop`)
- Orbital analysis (from `.molden` files)
- Geometry optimization tracking (multiple SCF cycles)
- More sophisticated parsing of `.out` files for edge cases

### 4.1 Proposed ORCA Step Taxonomy

**Step Type Names** (aligned with QMatSuite conventions):

- **Public Types** (generalized): `dft_scf`, `tddft`, `freq`, `nmr`, `mp2`, `ccsd`, `eom_ccsd`

**Mapping to QMatSuite Concepts**:

- **Step Type Registry**: Register ORCA step types in `src/quantumvitas/workflow/registry.py`
  - Engine family: `"orca"`
  - Machine type: `"orca_{method}"` (e.g., `"orca_dft_scf"`)
  - Public type: `"{method}"` (e.g., `"dft_scf"`)
  - Supports incremental skip: `True` for SCF/DFT, `False` for property steps (MVP)

- **Workflow Materialization**: Map generalized steps to ORCA-specific steps based on `engine_family="orca"`

**Step Type Examples**:

```python
# Step Registry Entry (pseudo-code)
"orca_dft_scf": StepTypeSpec(
    id="orca_dft_scf",
    engine="orca",
    public_type="dft_scf",  # Generalized step type

    supports_incremental_skip=True,  # Can skip if GBW exists
    requires_upstream_step=False,  # Standalone step
    produces_seed_artifact="gbw",  # Generates GBW file
)

"orca_tddft": StepTypeSpec(
    id="orca_tddft",
    engine="orca",
    public_type="tddft",
    machine_type="orca_tddft",
    supports_incremental_skip=False,  # Always rerun in MVP
    requires_upstream_step=True,  # Needs upstream SCF
    requires_seed_artifact="gbw",  # Needs upstream GBW
)
```

### 5.2 Risks

**Licensing**:
- **Risk**: ORCA is **proprietary** (not open-source)
  - Academic license: Free for academic use
  - Commercial license: Requires purchase
- **Mitigation**: 
  - QMatSuite does NOT bundle ORCA
  - Users must install ORCA separately
  - Clear documentation: "ORCA must be installed separately"
  - Engine reports "ORCA not found" if executable not detected

**Bundling Constraints**:
- **Risk**: Cannot distribute ORCA with QMatSuite
- **Mitigation**: 
  - Engine adapter only (no ORCA binary)
  - Executable detection (PATH or user-specified path)
  - Graceful degradation if ORCA not found

**User Must Install ORCA**:
- **Risk**: Additional installation burden for users
- **Mitigation**:
  - Clear installation instructions
  - Executable detection with helpful error messages
  - Optional engine (users can use QE/PySCF if ORCA not available)

**Version Drift**:
- **Risk**: ORCA input syntax changes between versions (4.x, 5.x, 6.0+)
- **Mitigation**:
  - Target ORCA 5.0+ for MVP (most common)
  - Version detection (parse `orca --version` output)
  - Input generation adapts to version (if needed)
  - Documentation: "Tested with ORCA 5.0+"

**Windows/macOS Specifics**:
- **Risk**: ORCA executable naming, path handling differs on Windows/macOS
- **Mitigation**:
  - Follow QE pattern: Platform-specific executable detection
  - Windows: `orca.exe`, macOS/Linux: `orca`
  - Use `shutil.which()` for PATH detection
  - Test on multiple platforms (if possible)

**Parallelism Complexity**:
- **Risk**: ORCA's MPI model differs from QE (no external MPI wrapper)
- **Mitigation**:
  - Do NOT use MPI wrapper (ORCA handles MPI internally)
  - Inject `%pal nprocs` in input file
  - Document: "ORCA manages MPI internally; do not use mpirun"

**GBW File Naming Constraints**:
- **Risk**: ORCA requires GBW filename to match input basename
- **Mitigation**:
  - Copy/link upstream GBW with correct name
  - Document naming constraints
  - Test GBW reuse in multi-step workflows

**Property File Availability**:
- **Risk**: `.prop` files may not be generated (user must request via `%output` block)
- **Mitigation**:
  - Always request `.prop` file in input generation (MVP)
  - Fallback to parsing `.out` if `.prop` not available
  - Document: "Property files are generated by default"
