# StepDoc.id vs meta.id vs ulid Usage Audit

**Date**: 2025-01-10  
**Purpose**: Document current semantics and usage patterns of step identifiers without changing them.

---

## Executive Summary

There is **semantic confusion** between:
- `Step.id` (returns **slug**, e.g., "scf")
- `Step.meta.id` (returns **ULID**, e.g., "01KEMHZJ7TZ74A4Q8PPSKMSCSV")
- `StepDoc` has **no id property** (inherits from `YamlDoc` which has no id property)

**Current state**: Codebase uses `step.id` in some places where ULID is needed, leading to bugs.

**Key finding**: `manifest_reconcile.py` was already fixed to use `step.meta.id`, but `runner.py` still uses `step.id` in dangerous places.

---

## 1. Current Semantics

### 1.1 StepDoc (YAML Document Wrapper)

**Location**: `src/quantumvitas/core/yamldoc.py:454`

```python
class StepDoc(YamlDoc):
    """Step document with QE-specific normalization."""
    # NO id property defined
```

**Key Facts**:
- `StepDoc` inherits from `YamlDoc`
- `YamlDoc` has **no `id` property** (it's just a document wrapper)
- To access step ID from `StepDoc`, you must read from data: `doc.get(["meta", "id"])` or `doc.export_copy()["meta"]["id"]`
- `StepDoc` does NOT have `meta` attribute as a Python object

**Access Pattern**:
```python
step_doc = StepDoc.load(path)
# WRONG: step_doc.id  # AttributeError
# WRONG: step_doc.meta.id  # AttributeError (no meta attribute)

# CORRECT: Read from data dict
meta = step_doc.export_copy().get("meta", {})
step_ulid = meta.get("id")
```

**Conclusion**: `StepDoc` has no `id` or `meta.id` attribute accessor.

---

### 1.2 Step (Calculation Step Object)

**Location**: `src/quantumvitas/calculation/step.py:34`

```python
@dataclass(slots=True)
class Step:
    meta: ResourceMeta  # Has id, name, slug, path, kind
    # ... other fields ...
    
    @property
    def id(self) -> str:
        """Legacy identifier accessor (maps to the slug inside ``meta``)."""
        return self.meta.slug  # RETURNS SLUG, NOT ULID!
```

**Key Facts**:
- `Step.id` returns `self.meta.slug` (human-readable slug like "scf", "nscf")
- `Step.meta.id` returns the **ULID** (26-char ID like "01KEMHZJ7TZ74A4Q8PPSKMSCSV")
- `Step.meta` is a `ResourceMeta` object with `id`, `name`, `slug`, `path`, `kind` fields

**Semantics**:
- `step.id` → **slug** (backwards compatibility, human-readable)
- `step.meta.id` → **ULID** (canonical identifier for registry/resolution)

**Conclusion**: `Step.id` is **ambiguous** - it's a slug, not a ULID. Use `step.meta.id` for canonical identifiers.

---

### 1.3 ResourceMeta.id

**Location**: `src/quantumvitas/core/resources.py:82`

```python
@dataclass(slots=True)
class ResourceMeta:
    id: str  # ULID (26 chars starting with "01")
    name: str
    slug: str
    path: str
    kind: ResourceKind
```

**Key Facts**:
- `ResourceMeta.id` is always a **ULID** (generated by `generate_resource_id()`)
- Stored in YAML as `meta.id` in step files
- Used by `ResourceIndex` for cross-resource resolution

### 2.3 Resolution Functions

**Location**: `src/quantumvitas/core/resolution.py:1254`

```python
def resolve_step(
    project_root: Path,
    calculation_selector: str,
    step_selector: str,  # Can be ULID OR slug
    config: Optional[dict] = None,
    index: Optional[ResourceIndex] = None,
) -> ResolvedResource:
```

**Key Facts**:
- `step_selector` accepts **both ULID and slug** (resolution tries ULID first, then slug)
- If you pass a slug, resolution may fail if multiple steps have the same type/slug
- **Best practice**: Always pass ULID for unambiguous resolution

**Usage**:
```python
# PREFERRED: Use ULID
require_step(project_root, calc_id, step.meta.id, ...)

# RISKY: Using slug (may be ambiguous)
require_step(project_root, calc_id, step.id, ...)  # Uses slug - may fail
```

## 3. Dangerous or Ambiguous Usages

### 3.1 Runner: require_step with step.id

**Files**: `src/quantumvitas/calculation/runner.py`

**Locations**:
- Line 305-306: `require_step(..., step.id, ...)`
- Line 409-410: `require_step(..., step.id, ...)`

**Issue**: `step.id` returns slug ("scf"), but `require_step` needs ULID for unambiguous resolution.

**Impact**: 
- May work if slug is unique within calculation
- Will fail if multiple steps share same type (e.g., two "scf" steps)
- Silent resolution to wrong step if slug matches earlier step

**Recommendation**: Replace with `step.meta.id`.

---

### 3.2 Runner: Manifest entries using step.id

**Files**: `src/quantumvitas/calculation/runner.py`

**Locations**:
- Line 424: `step_ulid=step.id`
- Line 558: `step_id=step.id`
- Line 584: `step_ulid=step.id`

**Issue**: Manifest expects ULID, but `step.id` returns slug.

**Impact**: 
- Manifest entries store slugs instead of ULIDs
- Reconciliation may fail to match steps correctly
- ULID-based step tracking breaks

**Recommendation**: Replace with `step.meta.id`.

---

### 3.3 StepDoc has no id accessor

**Issue**: `StepDoc` has no convenient way to access step ULID.

**Current Workaround**:
```python
step_doc = StepDoc.load(path)
meta = step_doc.export_copy().get("meta", {})
step_ulid = meta.get("id")
```

**Impact**: 
- Verbose access pattern
- Easy to miss meta access
- No type checking

**Recommendation**: Consider adding `StepDoc.meta` property or `StepDoc.id` property that returns ULID.

## 4. Suggested Clean Contract Options

### Option A: Keep id=slug, ulid separate (CURRENT, with fixes)

**Semantics**:
- `step.id` → slug (human-readable, for display/logging)
- `step.meta.id` → ULID (canonical, for resolution/registry)
- `StepDoc` → no id property (access via `export_copy()["meta"]["id"]`)

**Changes Needed**:
1. Fix `runner.py` to use `step.meta.id` for `require_step()` calls
2. Fix `runner.py` to use `step.meta.id` for manifest entries
3. Document that `step.id` is for display only

**Pros**:
- Backwards compatible (slug still accessible)
- Clear separation (slug vs ULID)

**Cons**:
- Easy to misuse (`step.id` looks like an ID but isn't)
- Requires discipline to use `meta.id` for resolution

---

### Option B: id=ulid (BREAKING CHANGE)

**Semantics**:
- `step.id` → ULID (canonical identifier)
- `step.slug` → slug (human-readable, NEW property)
- `StepDoc.id` → ULID (NEW property, reads from `meta.id`)

**Changes Needed**:
1. Change `Step.id` to return `self.meta.id` instead of `self.meta.slug`
2. Add `Step.slug` property returning `self.meta.slug`
3. Add `StepDoc.id` property returning ULID from data
4. Update all call sites that expected slug from `step.id`

**Pros**:
- Clear semantics (`id` always means ULID)
- Less confusion
- Type-safe

**Cons**:
- Breaking change (all code expecting slug from `step.id` breaks)
- Requires migration of all call sites
- May break external integrations

---

### Option C: Explicit properties (Hybrid)

**Semantics**:
- `step.id` → **DEPRECATED** (raises warning, returns slug for now)
- `step.ulid` → ULID (NEW, canonical)
- `step.slug` → slug (NEW, human-readable)
- `StepDoc.ulid` → ULID (NEW property)
- `StepDoc.slug` → slug (NEW property)

**Changes Needed**:
1. Add `Step.ulid` property
2. Deprecate `Step.id` (emit warning)
3. Add `StepDoc.ulid` and `StepDoc.slug` properties
4. Gradually migrate call sites to use explicit properties

**Pros**:
- Non-breaking (deprecation path)
- Clear semantics (explicit names)
- Gradual migration

**Cons**:
- More properties to maintain
- Deprecation period needed
